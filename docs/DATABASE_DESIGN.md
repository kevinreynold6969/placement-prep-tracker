# Database Design — Placement Preparation Tracker

> **Last Updated:** 2026-11-17 | **Database:** MongoDB Atlas | **ODM:** Mongoose

---

## Why MongoDB?

MongoDB is a document database — each record is a JSON-like document rather than a row in a table. This is appropriate for this application because:

1. **Flexible problem schema**: A problem can have optional fields (notes, approach, complexity). In a relational DB, these would be nullable columns or separate tables. In MongoDB, they are simply absent from the document.
2. **No complex joins needed**: Each problem belongs to one user. The relationship is simple — a `userId` field on the problem document is sufficient.
3. **Rapid iteration**: Adding a field to the schema does not require an ALTER TABLE migration.
4. **JavaScript native**: MongoDB stores BSON (Binary JSON), which maps naturally to JavaScript objects used throughout the Node.js backend and React frontend.

**Trade-off acknowledged**: MongoDB does not enforce referential integrity at the database level. If a user is deleted, their problems must be deleted by application code. This is handled in the user deletion service.

## Collections

### 1. `users`

Stores one document per registered account.

#### Schema

```javascript
{
  _id:        ObjectId,          // Auto-generated by MongoDB
  name:       String,            // Required, 2–50 characters
  email:      String,            // Required, unique, lowercase, trimmed
  password:   String,            // Required, bcryptjs hash (never the plaintext)
  createdAt:  Date,              // Auto-managed by Mongoose timestamps
  updatedAt:  Date               // Auto-managed by Mongoose timestamps
}
```

#### Field Explanations

| Field | Type | Required | Unique | Notes |
|---|---|---|---|---|
| `_id` | ObjectId | auto | yes | MongoDB primary key |
| `name` | String | yes | no | Display name, 2–50 chars |
| `email` | String | yes | yes | Lowercased before save, used as login identifier |
| `password` | String | yes | no | bcryptjs hash, cost factor 12. Never returned in API responses |
| `createdAt` | Date | auto | no | Mongoose `timestamps: true` |
| `updatedAt` | Date | auto | no | Mongoose `timestamps: true` |

#### Indexes

- `email`: unique index (enforced by MongoDB) — prevents duplicate accounts and speeds up `findOne({ email })` lookups during login.

#### Illustrative Schema Example (NOT real user data)

```json

  "_id": "507f1f77bcf86cd799439011",

  "createdAt": "2026-11-01T10:00:00.000Z",
  "updatedAt": "2026-11-01T10:00:00.000Z"
}
```

### 2. `problems`

Stores one document per problem a user has recorded.

#### Schema

```javascript
{
  _id:              ObjectId,    // Auto-generated
  userId:           ObjectId,    // Required — references users._id
  title:            String,      // Required, 2–200 characters
  platform:         String,      // Enum: LeetCode | Codeforces | HackerRank | CodeChef | GeeksForGeeks | Other
  url:              String,      // Optional, external problem URL
  topic:            String,      // Required, enum of 18 DSA categories
  difficulty:       String,      // Required, enum: Easy | Medium | Hard
  status:           String,      // Required, enum: not_attempted | attempted | solved | needs_revision
  dateAttempted:    Date,        // Optional, when first attempted
  notes:            String,      // Optional, general notes, max 2000 chars
  approach:         String,      // Optional, solution strategy, max 2000 chars
  timeComplexity:   String,      // Optional, e.g. "O(n log n)"
  spaceComplexity:  String,      // Optional, e.g. "O(n)"
  needsRevision:    Boolean,     // Required, default false
  revisedAt:        Date,        // Optional, last time user marked as revised
  createdAt:        Date,        // Mongoose timestamps
  updatedAt:        Date         // Mongoose timestamps
}
```

#### Field Explanations

| Field | Type | Required | Notes |
|---|---|---|---|
| `userId` | ObjectId | yes | Foreign key to `users`. All queries filter by this — prevents one user seeing another's data |
| `title` | String | yes | The problem name, e.g. "Two Sum" |
| `platform` | String | yes | Enum. Restricts to known platforms |
| `url` | String | no | Direct link to the problem for quick access |
| `topic` | String | yes | One of 18 DSA topics. Used for topic-wise analytics |
| `difficulty` | String | yes | Easy / Medium / Hard. Used for difficulty analytics |
| `status` | String | yes | The core tracking field. Defaults to `not_attempted` |
| `dateAttempted` | Date | no | Allows activity-over-time queries |
| `notes` | String | no | Personal notes, mistakes, reminders |
| `approach` | String | no | Algorithm / approach used |
| `timeComplexity` | String | no | Big-O time complexity |
| `spaceComplexity` | String | no | Big-O space complexity |
| `needsRevision` | Boolean | yes (default: false) | Powers the revision list feature |
| `revisedAt` | Date | no | Tracks when the user last marked this as revised |

#### Indexes

- `{ userId: 1 }` — most queries filter by userId; this index makes them fast.
- `{ userId: 1, topic: 1 }` — compound index for topic-filtered queries by user.
- `{ userId: 1, status: 1 }` — compound index for status-filtered queries.
- `{ userId: 1, needsRevision: 1 }` — compound index for revision list queries.

```json
{
  "_id": "507f191e810c19729de860ea",
  "userId": "507f1f77bcf86cd799439011",
  "title": "Two Sum",
  "platform": "LeetCode",
  "url": "https://leetcode.com/problems/two-sum/",
  "topic": "Hashing",
  "difficulty": "Easy",
  "status": "solved",
  "dateAttempted": "2026-11-10T00:00:00.000Z",
  "notes": "Used a hash map to store complement values.",
  "approach": "HashMap approach: store target-current in map, check if current exists in map.",
  "timeComplexity": "O(n)",
  "spaceComplexity": "O(n)",
  "needsRevision": false,
  "revisedAt": null,
  "createdAt": "2026-11-10T08:30:00.000Z",

```

## Relationships

```
users (1) ────────── (many) problems
  _id      ◄──────────── userId
```

This is a **one-to-many** relationship implemented via a reference (foreign key pattern). Each problem stores the `ObjectId` of the user who created it.

**Why not embed problems inside the user document?**
MongoDB supports embedding documents. However, embedding all problems inside the user document would:
- Create a document that grows unboundedly as problems are added.
- Make it impossible to query or paginate problems efficiently.
- Hit MongoDB's 16MB document size limit for heavy users.

Using a reference with a `userId` field is the correct approach here.

The following values are enforced at the Mongoose schema level:

```
Arrays, Strings, Hashing, Two Pointers, Sliding Window, Prefix Sum,
Binary Search, Sorting, Greedy, Stack, Queue, Linked Lists, Trees,
Binary Search Trees, Heaps, Graphs, Backtracking, Dynamic Programming
```

## Status Enum

```
not_attempted  — Problem added but never attempted
attempted      — Tried but not solved
solved         — Successfully solved
needs_revision — Solved but identified as needing review
```

## Why Only Two Collections?

A common question. The alternative would be:
- A separate `topics` collection with topic documents.
- A separate `revisions` collection tracking each revision event.

For this application scope, keeping topics as an enum field in the problem document is correct because:
- Topics are a fixed list that does not change per user.
- There is no per-user topic configuration needed.
- The enum approach is simpler and equally queryable.

Revisions could be a separate collection if we wanted to track the full revision history (each time a problem was revised, with timestamps). That is a reasonable future enhancement and is documented in KNOWN_ISSUES.md.
